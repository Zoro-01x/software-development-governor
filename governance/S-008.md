# S-008 — Deterministic Builds

Constitution text: *"The same source and requirements shall produce the same
output. Build processes shall be repeatable and idempotent. A build that
introduces non-determinism (e.g., unreproducible dependencies, timestamp
injection, network-dependent behavior) is a defect."*

---

## STEP 2 — Problem

A build that behaves differently on the second run cannot be debugged, audited,
or trusted. The output of a build is only meaningful if the same inputs produce
the same artifacts every time. This rule classifies any non-determinism source
as a defect and refuses the build.

## STEP 3 — Concepts

- deterministic build
- idempotent
- non-determinism source
- defect

## STEP 4 — Deterministic Definitions

| Concept | Definition |
|---------|-----------|
| build input | The tuple (source snapshot, requirement set, build configuration). |
| deterministic | Two executions with identical build input produce byte-identical outputs. |
| idempotent | Executing the build twice from the same input yields the same output (determinism restricted to repetition). |
| non-determinism source | Any declared or observed factor in the enumerated list: unreproducible dependencies (floating versions, mutating registries), timestamp injection into outputs, network-dependent behavior at build time, unordered iteration with side effects. |
| defect | A build that is NOT deterministic, i.e., whose output hashes differ across identical-input runs, OR whose configuration declares any non-determinism source. |

## STEP 5 — Required State

- `build.inputFingerprint` (hash of source + requirements + config)
- `build.outputHashes[]` (per run)
- `build.nonDeterminismSources[]` (declared)
- `dependencies[]` (version pinning — see S-012)

## STEP 6 — Triggers

- At build completion (compare output hashes across identical-input runs)
- At build configuration change

## STEP 7 — Algorithm

```
IF build = undefined OR build.inputFingerprint = ''
  THEN fail: "No build record with an input fingerprint."

IF build.nonDeterminismSources ≠ []
  THEN fail: "Build declares non-determinism sources: {list}."

IF |build.outputHashes| < 2
  THEN fail: "Build has fewer than two identical-input runs — determinism unverified."

IF set(build.outputHashes) ≠ {single hash}
  THEN fail: "Build outputs differ across identical-input runs."

// dependency pins required so future runs can't drift
FOR each dependency ∈ dependencies:
  IF version is floating (undefined or contains wildcard)
    THEN fail: "Dependency '{name}' is not pinned."

pass
```

## STEP 8 — Tests

| Class | Case | Expected |
|-------|------|----------|
| normal | Two identical-input runs, same output hash, no sources | pass |
| failure | Output hashes differ across runs | fail |
| failure | Declared non-determinism source (e.g., timestamp injection) | fail |
| failure | Network fetch at build time declared | fail |
| edge | One run only | fail (determinism unverified — needs ≥2) |
| edge | Floating dependency version | fail (pin required) |
| regression | Determinism check after requirement amendment (same source) | pass |
| adversarial | Hash collision: output differs but hashes equal | fail (hash function must be collision-safe — output bytes compared, not only hashes, when available) |
| adversarial | Non-determinism source hidden behind cache layer | fail (declaration is mandatory — undeclared but observed variation also fails via hash comparison) |

## STEP 9 — Conflicts

- S-009 (Reproducible Verification) governs test outcomes; S-008 governs build
  artifacts. Both isolate from uncontrolled external state. No conflict.
- S-012 requires pinned, approved dependencies — this rule consumes the pin
  requirement. No conflict.
