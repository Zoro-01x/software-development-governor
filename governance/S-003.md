# S-003 — Specification Authority

Constitution text: *"Specifications outrank implementation. When a specification
and its implementation disagree, the implementation is defective by definition."*

---

## STEP 2 — Problem

When code and spec disagree, teams often "fix" the spec to match the code —
letting implementation silently redefine requirements. This rule makes the
direction of authority explicit: the spec is the source of truth. Disagreement
means the implementation is defective, and the spec may only change through an
approved amendment, never through implementation.

## STEP 3 — Concepts

- specification
- implementation
- contradiction
- defective
- requirement amendment

## STEP 4 — Deterministic Definitions

| Concept | Definition |
|---------|-----------|
| specification | The set of Approved Requirements (GLOSSARY §3) plus the approved engineering architecture (S-011). |
| implementation | The artifacts produced for the traced requirements (kind ∈ {source, configuration, deployment}). |
| contradiction | A requirement mandates behavior X for artifact A AND artifact A's record or content specifies behavior NOT X. Detected by an automated conformance check (e.g., test outcome vs. requirement text mapping). |
| defective | An implementation containing ≥1 contradiction with its governing specification. |
| requirement amendment | GLOSSARY §4. |

## STEP 5 — Required State

- `requirements[]` (approved text)
- `artifacts[]` (implementation + their declared conformance)
- `verificationRuns[]` (evidence of conformance)
- `decisions[]` (amendments)

## STEP 6 — Triggers

- At acceptance of any implementation
- At change-control review, when a spec change is proposed

## STEP 7 — Algorithm

```
// Direction 1: implementation acceptance
FOR each artifact ∈ implementation:
  reqs = tracedRequirements(artifact)          // GLOSSARY §10
  FOR each req ∈ reqs:
    conformance = automatedCheck(req, artifact) // S-002 evidence
    IF contradiction(req, conformance)
      THEN fail: "Artifact '{artifact.id}' contradicts requirement '{req.id}'. Implementation is defective by definition."

// Direction 2: proposed spec change
IF proposed amendment exists:
  IF NOT humanApproved(amendment)               // GLOSSARY §2, S-006
    THEN fail: "Specification cannot be changed without an approved amendment."
  // the amended requirement enters the next evaluation cycle as new approved text

pass
```

## STEP 8 — Tests

| Class | Case | Expected |
|-------|------|----------|
| normal | Implementation conforms to all traced requirements | pass |
| failure | Implementation contradicts one requirement | fail, defect named |
| failure | Spec change proposed without human approval | fail |
| edge | Requirement amended (human-approved) then implementation updated | pass against new text |
| edge | Requirement text empty | fail (no valid spec — GLOSSARY §3) |
| regression | S-001 order: unapproved requirement cannot be contradicted because it cannot be traced | compose cleanly |
| adversarial | Implementation metadata claims conformance but the supporting run is stale (S-002) | fail |
| adversarial | Amendment approved after implementation shipped, used to excuse the defect | fail — amendment applies forward only |

## STEP 9 — Conflicts

- S-011 (Architectural Integrity) is this rule applied to the architecture as
  specification. Same verdict semantics, disjoint inputs. No conflict.
- S-006 defines who may approve amendments (humans); this rule requires the
  amendment. No conflict.
