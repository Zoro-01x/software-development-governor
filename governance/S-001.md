# S-001 — Requirements Before Implementation

Constitution text: *"No code shall be produced without an approved requirement
it satisfies."*

---

## STEP 2 — Problem

Code gets written because it seems useful, or because someone started typing.
Without a requirement that is APPROVED and TRACED to the work, the code is
speculative: ungoverned, untraceable, and unverifiable against intent. This rule
makes an approved requirement a precondition for executing any implementation
task.

## STEP 3 — Concepts

- code
- requirement
- approved requirement
- implementation task
- trace
- decision log

## STEP 4 — Deterministic Definitions

| Concept | Definition |
|---------|-----------|
| code | Any artifact of kind `source` produced by the task. |
| approved requirement | GLOSSARY §3. |
| implementation task | A request of type `implementation` with an artifact set. |
| trace | GLOSSARY §10: the task declares `requirementIds`; each must map to a requirement record. |
| executed | The task is allowed to produce code. |

## STEP 5 — Required State

- `request.type`
- `request.requirementIds[]` (task-declared trace)
- `requirements[]` (status + approval records)
- `decisions[]` (approval decisions)

## STEP 6 — Triggers

- BEFORE executing an implementation task (at task start, not at file-write time)
- Re-evaluated if any traced requirement is amended or revoked mid-task

## STEP 7 — Algorithm

```
IF request.type ≠ 'implementation' THEN continue

taskRequirements = request.requirementIds

IF taskRequirements = ∅
  THEN fail: "No requirement traced to this implementation task."

FOR each reqId ∈ taskRequirements:
  req = requirements.find(id = reqId)
  IF req = undefined
    THEN fail: "Traced requirement {reqId} does not exist."
  IF NOT isApprovedRequirement(req)   // GLOSSARY §3
    THEN fail: "Requirement {reqId} is not approved."

pass
```

## STEP 8 — Tests

| Class | Case | Expected |
|-------|------|----------|
| normal | Task traces to one approved requirement | pass |
| normal | Task traces to multiple approved requirements | pass |
| edge | Requirement approved at task start, revoked during task | fail on re-evaluation |
| edge | Empty requirement id list on non-implementation request | rule not applicable |
| failure | Task traces to nothing | fail |
| failure | Traced id does not exist | fail |
| failure | Traced requirement status = `draft` | fail |
| failure | Traced requirement approved via decision with `decision` = `RETRIEVE_EVIDENCE` | fail |
| regression | Approved requirement + passing tests still satisfies S-002/S-004 | compose cleanly |
| adversarial | Requirement id reused by two distinct requirement records | fail (id must be unique — check duplicates) |
| adversarial | Approval decision recorded AFTER task execution timestamp | fail (approval must predate execution) |

## STEP 9 — Conflicts

- S-005: an approved assumption is a requirement amendment (GLOSSARY §11) and
  therefore satisfies this rule if recorded as an Approved Requirement.
  Resolution recorded in governance/README.md Conflict Register.
- S-010: minimal change is scoped to the traced requirements — no conflict.
