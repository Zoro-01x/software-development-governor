# S-004 — Test-Bound Development

Constitution text: *"Every implementation claim must be demonstrated by automated
verification. The set of claims that cannot be automatically verified shall be
explicitly documented as accepted risks."*

---

## STEP 2 — Problem

Teams claim "the module handles empty input" and nobody can disprove it until it
explodes in production. This rule makes the claim un-accepted until a passing
automated check exists. Claims that CANNOT be checked automatically are not
ignored — they are forced into an explicit accepted-risk register with an owner
and rationale.

## STEP 3 — Concepts

- claim
- automated verification
- verifiable claim
- accepted risk

## STEP 4 — Deterministic Definitions

| Concept | Definition |
|---------|-----------|
| claim | GLOSSARY §8. |
| automatically verifiable | A claim for which a deterministic automated check exists that can return pass/fail (boolean check, not judgment). |
| demonstrated | A claim is demonstrated iff a Passing Automated Verification (GLOSSARY §7) exists for its target artifact. |
| accepted risk | GLOSSARY §12: `unverifiable=true`, non-empty `owner`, non-empty `rationale`. |
| claim disposition | One of: `verified` (demonstrated), `accepted-risk` (unverifiable + documented), `unmet` (everything else). |

## STEP 5 — Required State

- `claims[]` (`unverifiable`, `owner`, `rationale`, `targetArtifactId`)
- `verificationRuns[]`
- `artifacts[]`

## STEP 6 — Triggers

- On claim registration
- At implementation completion (final disposition sweep)

## STEP 7 — Algorithm

```
FOR each claim ∈ claims:
  IF claim.unverifiable = true:
    IF owner ≠ '' AND rationale ≠ ''
      THEN claim accepted as risk (continue)
      ELSE fail: "Unverifiable claim '{claim.id}' lacks owner or rationale."
  ELSE:
    runs = verificationRuns.filter(isPassingAutomatedVerification AND
           targetArtifactId = claim.targetArtifactId AND
           sourceVersion = artifact.sourceVersion)
    IF runs = ∅
      THEN fail: "Claim '{claim.id}' is not demonstrated by automated verification."

pass
```

## STEP 8 — Tests

| Class | Case | Expected |
|-------|------|----------|
| normal | Verifiable claim with passing run | pass |
| normal | Unverifiable claim with owner + rationale | pass (accepted risk) |
| failure | Verifiable claim, no run | fail |
| failure | Verifiable claim, failing run | fail |
| failure | Unverifiable claim, no owner | fail |
| failure | Unverifiable claim, empty rationale | fail |
| edge | Claim both `unverifiable` and backed by a passing run | pass as verified (verification wins) |
| edge | Zero claims | pass (vacuous) |
| regression | S-002 and S-004 both evaluate the same claim set | identical dispositions |
| adversarial | Claim marked `unverifiable` to dodge a trivial check | fail if a deterministic check exists for the claim text (registry of checkable claim patterns) |
| adversarial | Accepted-risk record references a different claim id | fail (must link to the claim) |

## STEP 9 — Conflicts

- S-002 (Code Is Evidence): identical standard, negative/positive forms.
- S-010 (Incremental Change): accepted risks are documentation artifacts and
  must trace like any artifact (S-007). No conflict.
